## 2. 问答分析题

### 2.1 简述下图执行计划的执行过程

题图是 `SELECT R.id, S.cdate FROM R JOIN S ON R.id = S.id WHERE S.value > 100` 的火山模型（迭代器模型）。每个算子都实现一个 `Next()`，上层算子每调用一次下层的 `Next()`，下层就返回一行，执行由根节点向下"拉"数据：

1. 执行器反复调用根节点——投影算子 π 的 `Next()`，每返回一行就输出一行结果。
2. π 调用子节点 Join 算子的 `Next()`。
3. Join 第一次被调用时，先进入**构建阶段**：循环调用左子树（R 的扫描）的 `Next()`，R 的扫描每次返回一行，Join 把它插入 HASH 表，直到 R 读完。
4. 然后进入**探测阶段**：调用右子树——选择算子 σ 的 `Next()`。σ 再调用 S 的扫描的 `Next()` 取一行，判断 `value > 100`，不满足就继续取下一行，满足才返回给 Join。
5. Join 用这一行的 `S.id` 到 HASH 表中查找，找到匹配的 R 行，就把拼接后的行返回给 π；π 只保留 `R.id、S.cdate` 两列后输出。
6. 重复 4、5，直到 S 读完、σ 返回空，Join 也返回空，π 返回空，执行结束。

整个过程中一行数据一产生就逐层向上传递，不必等下层全部做完（HASH 表的构建阶段除外），中间结果不需要全部物化。

## 3. 思考题：数据库与商业应用软件的演进关系，以及对 AI 系统未来发展的启示

早期的应用把数据存在自己定义的文件里，读写逻辑和业务逻辑写在一起，换一种查询方式就要改程序。层次、网状数据库把数据管理独立出来，但应用仍要沿着指针一步步"导航"取数据，数据结构一变，应用就得跟着改。关系模型把"要什么"和"怎么取"分开：应用只用 SQL 描述要什么，怎么取交给优化器和执行器。数据独立性带来了 ERP、CRM、银行核心系统这类大型商业软件的爆发——业务开发者不需要懂存储，数据库厂商则可以在 SQL 不变的前提下持续优化内核。

此后的演进也一直是这个关系：应用的规模和形态变了（互联网、移动、分析型业务），数据库就出现新的形态（分布式、列存、LSM-Tree、云原生），但声明式接口始终保留，变化被封装在接口之下。

对 AI 系统的启示：

1. **接口要稳定、要声明式**。今天调用大模型还像早期"导航式"访问：提示词、工具调用、上下文拼接都由应用自己管理，换个模型就要重写。AI 系统可能也会走向"说明要什么，系统决定怎么做"，由类似优化器的组件来选模型、选工具、安排执行顺序。
2. **基础软件的价值在内核**。课上讲到数据库纯算法层面已很难进步，竞争转向与硬件体系结构的结合（PMC、SIMD、存储介质）。AI 系统同样如此：模型能力趋同之后，推理引擎、显存与存储管理、调度这些"内核"会决定成本和性能。
3. **可观测性先行**。数据库靠执行计划、统计信息、PMC 这类手段才能被调优；AI 系统若要承载关键业务，也需要能解释、能度量的执行过程，而不是只有输入和输出。
