# 课5（10月29日）：存储引擎与接口实现原理

## 1. 选择题

| 题号 | 答案 | 理由 |
|---|---|---|
| 1.1 | BD | 存储引擎管理的是存储空间与 I/O，不局限于"文件"；它可以建在文件系统之上（如 PG 的 md.c），也可以绕过文件系统直接管理块设备，两者并不冲突，所以 C 错 |
| 1.2 | ABCD | 文件系统就是操作系统的"存储引擎"；存储引擎的核心是空间元数据的管理与检索，FAT 等结构就是这种元数据；元数据量大、访问频繁，快速检索是难点 |
| 1.3 | BD | A 错：元数据会随数据量增长，遍历无法支撑；C 错：主流文件系统多用 B+树（XFS、Btrfs，ext4 的 extent 树和目录 HTree 也是树形结构），并非都用 HASH；D 对：BTree 的页在内存缓存中与在存储设备上格式一致，读入后不用转换即可使用 |
| 1.4 | D | 接口结构中定义为 `void (*smgr_open) (SMgrRelation reln);`，openHalo 源码 `smgr.c` 中一致 |
| 1.5 | ACD | 文件号是进程打开文件表的下标，内核凭它找到 `struct file`，其中有读写位置（文件指针）和指向 inode 等元数据的信息，所以 A 对；B 不是文件号的作用；PG 的 `Vfd` 结构第一个成员就是 `fd`，并在其上实现了 LRU 管理，突破操作系统对打开文件数的限制，相当于在文件系统之上又加了一层，所以 C、D 对 |
| 1.6 | BD | Intel、AMD、ARM 以及国产 CPU 都有 PMC，A 错；PMC 能统计 cache、TLB、分支预测、访存等数百种事件，C 错；PMC 虽是硬件，但配置计数器要在内核态写 PMU 寄存器，计数器的多路复用、进程切换时的保存恢复也由内核完成，应用只能经操作系统接口（Linux 的 perf_event_open、prctl）使用，大作业 HaloPMC 正是如此，所以 D 对 |
| 1.7 | C | 能同时打开的计数器数量取决于记录计数结果的寄存器数量（约 10 个），这也是 HaloPMC 中 `PMC_NUM` 定为 10 的原因；超过时内核只能分时复用 |
| 1.8 | C | 读取计数器本身会产生访存，过多会干扰被观测程序；同时芯片面积宝贵，可观测性硬件不宜过多 |

## 2. 问答分析题

### 2.1 为什么 PMC 类功能会成为现代处理器的标配

1. **性能瓶颈从"算得慢"变成了"等得久"**。现代 CPU 有多级 cache、乱序执行、分支预测、预取，程序的快慢更多取决于 cache 是否命中、分支是否猜对、流水线是否停顿。这些都发生在硬件内部，软件看不见，计时也只能告诉你"慢了"，不能告诉你"为什么慢"。只有 CPU 自己能统计这些事件。

2. **软件方法测不准**。在程序里插桩计时、用模拟器跟踪，要么开销太大，要么改变了被测程序的行为。PMC 由硬件在每个周期并行计数，几乎没有开销，是唯一能在真实负载下精确"画像"的手段。大作业中也看到：哪怕只是用 prctl 开关计数器，系统调用的开销就足以让结果严重失真。

3. **整个软件栈都要靠它调优**。编译器做反馈优化（PGO、AutoFDO）、操作系统做调度、数据库和 JVM 等基础软件做热点优化，都依赖 PMC 数据。云厂商还用它做性能监控和故障诊断。

4. **芯片厂商自己也需要**。新微架构的验证、性能调优，以及向客户证明性能，都需要硬件计数器。

5. **代价很小**。计数器和少量寄存器只占很少的芯片面积，又能显著提高整个软件生态的效率，投入产出比很高。

所以 Intel、AMD、ARM 以至国产 CPU 都把 PMC 作为标准配置，Linux 也提供了 perf_event 这套通用接口。
